Northern Hemisphere Home Park characterization

Historical pre-fix characterization: the assertions and helper-call order in this
suite describe the original failures, not the corrected implementation. The tests
were not updated or run as part of the Polar Home Park fix.

Corrected behavior:
- Custom Home Park azimuth is local in both hemispheres and is converted to the
  northern storage convention before calling AzAltToPolarPark.
- DetermineIfThroughPole requires application axes and uses only the normalized
  Dec axis, with the same pole tolerance as SideOfPier. RA does not indicate a flip.
- SkyWatcher Left reflects Y in both hemispheres. Southern X is negated, making
  AxesAppToMount the inverse of AxesMountToApp and matching reflected hardware limits.
- Simulator keeps its existing effective Right mode regardless of selected side;
  its mapping and limits were already consistent. No Left simulation was added.
- Default keeps its [90,90] override and bypasses custom validation. Custom positions
  are no longer mistaken for Default just because altitude equals abs(latitude).
- Home and AutoHome settings are only written after custom park validation succeeds.

Original suite usage and pre-fix results follow. Update its expectations and pass
application axes to orientation checks before using it as a regression suite.

Run HomeParkCharacterizationTests in Visual Studio Test Explorer. The grid test
attaches home-park-grid.csv.gz and home-park-summary.csv to its result and writes
the test-host artifact paths to its output. The CSV uses invariant-culture numbers;
its rows are ordered by mount, requested side, latitude, profile, azimuth and altitude.
Each profile has exactly 361 x 181 = 65,341 points. The tested latitudes are 1, 30,
52, 80 and 52.25 degrees. The explicitly selected (X limit, lower Y, stored upper Y)
profiles are (105,20,50), (150,-30,70), and (210,-90,90), all selectable in the
hardware limits UI. This is not exhaustive over continuous site latitudes or hardware
settings. The 60 configurations produce 3,920,460 rows. Simulator's effective side
is always Right even if Left is selected.
The compressed CSV contains actual conversion, physical mapping, limits, pole
classification and the decision in dialog order. The summary counts decisions and
includes the first witness for a normal converted position flagged through-pole.
Such a flag is suspicious, not an assertion that rejection is correct.

The tests call the production conversion, SlewPark mapping, limit and pole helpers.
They reconstruct only the dialog's short-circuit decision order; they do not invoke
AcceptHomeSettingsDialog, WPF bindings, UI resources, saving, or park-position updates.
In particular the default [90,90] override and its skipped validation are documented
from source, not exercised end-to-end. There is no telescope connection or UI launch.
Tests access existing backing fields instead of persistent settings setters, restore
those fields in finally/Dispose, and are marked nonparallel. The production SkyServer
initializer can migrate/save settings; the fixture refuses to initialize when the
current profile has no existing version or alignment settings require an upgrade.
It does not sandbox other tests or the server's unrelated initialization side effects.

Reproduction: latitude 52, X limit 105, lower Y 20, displayed/stored upper Y 50;
select Custom Home Park azimuth 180 and altitude 70. The converted app axes are
[0,32]. SkyWatcher Left maps this to [0,148], passes limits, then rejects through-pole.
SkyWatcher Right and Simulator Left/Right accept [0,32]. Four named data-row cases
assert these exact outcomes. Do not command a physical slew solely from these tests.

Do not treat the grid's decision as a normative reachability oracle. Independent
unit-vector checks verify the sky direction, and targeted boundaries characterize
current helpers; they cannot establish whether a physical mount should reject a slew.
The suspicious flag means an in-limits target with abs(appY) below 90 degrees,
excluding the singular pole, was classified through-pole using physical axes.
Run only this test class: existing alignment tests have cleanup that writes model
files and can fail under parallel execution.
